On Agentic Software

Essay · January 25, 2025 · 4 min read

In the spirit of transparency, I’ll admit: I need to squint to see how available “agentic software” is anything more than an industry-wide pivot to a text-based UX pattern with some promising functionality that catastrophically fails about ~5% of the time.

I start here because I know others share this skepticism in some form or another, so a discussion of the fundamentals of “traditional software” contrasted to the fundamentals of emerging “agentic software” is worthwhile.

I define “traditional software” as a collection of digital tools that help end users complete a set of tasks. This means effectively all traditional software companies do some version of the following:

  • listen to users describe a bunch of things they need to do
  • design intuitive digital solutions to help them do those things
  • implement those digital solutions in a scalable and stable way
  • rinse and repeat, bonus points for identifying adjacent growth verticals

Every PED (‘Product, Engineering, and Design’) role at a traditional software company can be mapped to one of these four core actions or some combination thereof. By this definition, traditional software development is best understood as a repeating process of feature ideation, creation and distribution on top of an ever-expanding product surface.

Having more features has obvious benefits but there are also clear negative externalities. Chief among such negative externalities is that as a product surface combines more and more features, and as a result becomes more and more complex, the requirements of “design systems” and “context sharing” becomes more and more intrusive, which then demands more and more of the time of PED functions as a proportion of everything else they do.

Consider how much time is spent thinking about relative feature prioritization, UI implementations, and UX testing at Ramp (hint: it’s a lot). To be clear, to create great traditional software, allocating time to these development pillars makes sense, which is why they are such a point of emphasis. They just take up a lot of time.

And Ramp is best-in-class. Greener pastures are far and few between.

Sure, feature consolidation is possible, but it is often on the margin and it is rarely a consistent focus. For companies building traditional software at scale, ensuring “tasteful expansion” becomes the name of the game. Fail and you become Salesforce and its army of third-party implementation consultants. The only worse fate would be losing deals due to a lack of feature parity. “Agentic software” is primed to follow a very different development cycle.

I define agentic software as a collection of tasks that can be successfully completed without human intervention given a set of defined digital inputs. The transition to successful task completion from feature availability has far-reaching implications. First, agentic software quality can be universally measured with only two questions:

  • can the software successfully complete tasks at an acceptable accuracy?
  • what tasks are available within the software?

In the maximalist sense, there is no user experience to consider. The best possible version of any agentic software is that which successfully completes the task it claims to be able to complete with perfect accuracy and no human intervention whatsoever. To that end, all that matters is the agent’s success rate and the agent’s accuracy with input quality held constant. Whether the interaction with the software is pleasant or intuitive or efficient is not material; the interaction itself is a failure. More simply, agentic software compresses the user experience to a single evaluation and that evaluation has nothing to do with the user’s interaction with said software. That’s weird! Users usually talk about their experience with software based on how they feel about it over time with consistent use.

Second, and in a similarly maximalist sense, product differentiation is achieved by diminishing interaction, not increasing interaction. Agentic software is fundamentally better if the way by which you collect inputs is somehow repeatable or predictable such that you do not have to do it often or even at all. Again that’s weird! Development teams are usually incentivized to create software experiences that users enjoy and come back to but now they are most successful if users do not interact with the software at all.

The implication is that agentic software is user experience agnostic; all that matters is outcome performance. A customer is no longer paying for the experience and ability to do things a certain way but instead paying for the things to simply be done so he or she can do other things.
